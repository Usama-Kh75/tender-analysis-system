# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

نظام تحليل العطاءات التجاري المتكامل — a generic commercial tender/bid analysis system for Iraqi government (or private-sector) tender committees, not tied to any specific entity. It automates the financial audit work of a tender-opening committee: comparing bidder prices against the estimated cost (الكلفة التخمينية), detecting arithmetic errors and discrepancies between numeric and Arabic-spelled-out (تفقيط) amounts, computing deviation percentages, and producing an official printable committee report — per Iraq's "تعليمات تنفيذ العقود الحكومية لعام 2025" (2025 Government Contract Execution Instructions). The contracting entity's name is a per-project setting (`TenderProject.entityName`), not hardcoded.

**Deployment model is a hard constraint**: the deliverable is a single portable `نظام_تحليل_العطاءات.html` file that any committee member can copy to any Windows PC and just open — no install, no server, no database, no internet required for core use (internet is only needed for the optional AI OCR engine). Do not introduce dependencies that require installing anything on the end-user's machine (local LLM runtimes, native helper apps, local servers/daemons) — this has been explicitly rejected before in favor of portability. Data lives only in the browser's `localStorage`; there is no backend.

```bash
npm install       # install dependencies

npm run build       # tsc -b type-check, then vite build (outputs dist/index.html)
npm run lint        # oxlint
npm run check       # pure-function checks (checks/*.test.ts via rolldown + node --test)
```

`npm run check` runs the pure-function checks in `checks/` (bundled with rolldown, which ships with Vite, into `checks/.out`, then `node --test`; `xlsx-js-style` is bundled in because Node does not expose its CJS named exports). UI is still verified by hand.

### Publishing a change to the standalone HTML file

The single-file deliverable is **not** auto-generated on every edit — after making changes under `src/`, you must rebuild and manually refresh it:

```bash
npm run build
cp dist/index.html "نظام_تحليل_العطاءات.html"
```

Since v1.14.0 the built `نظام_تحليل_العطاءات.html` is git-ignored (it made every commit ~6 MB). It stays on disk for the user, and each release attaches it to a GitHub Release: `gh release create vX.Y.Z "نظام_تحليل_العطاءات.html" --title vX.Y.Z`. To get an old version, check out its tag and rebuild, or download it from Releases.

(`vite-plugin-singlefile` inlines all JS/CSS into one `dist/index.html`; the copy step is what the end user actually opens via `تشغيل_النظام.bat`.) Always run `npm run build` (which runs `tsc -b` first) before considering a change done — it is the project's only type/build check.

### Installable web app (PWA)

The same build is also deployed to GitHub Pages (`https://usama-kh75.github.io/tender-analysis-system/`) so it can be installed as a Windows app from Edge/Chrome. `.github/workflows/pages.yml` deploys **only on a `v*` tag push** (not every push) — the installed app fetches the latest deployed version, so every release must be deliberate: bump `package.json` version, **if (and only if) the release adds a new function or addition that changes how the system is used, add a short Arabic entry at the top of `CHANGELOG` in `src/changelog.ts`** phrased as what the user can now do. Never explain changes there: no fixes, refactors or UI tweaks, and no improvements to existing features such as better reading, extra checks or flags, or clearer labels (user's explicit decision, tightened 2026-10-05). A release without such an addition gets no entry and shows no «ما الجديد» dialog, commit, then `git tag vX.Y.Z && git push origin vX.Y.Z`. The build also emits `dist/version.json`; an open app polls it (`checkForUpdate` in `src/pwa.ts`) and shows an «يتوفر إصدار جديد» banner (`src/components/UpdateNotice.tsx`). Its «حفظ والتحديث» button refuses to reload while a modal holding unapplied work is open (`blockingWork` in `App.tsx` — add any new such modal there), then saves the active tab + scroll position to sessionStorage (`src/resume.ts`) and restores them after the reload; project data itself needs no extra save because App persists `projects` to localStorage on every change. `RELEASE_STAGE` in `src/changelog.ts` appends "Beta" to the version in the UI only — never in the printed محضر; set it to `''` when the user declares the system stable. PWA pieces: `public/manifest.json` + icons, `pwa/sw.js` (template; the `serviceWorker()` plugin in `vite.config.ts` emits `dist/sw.js` with the version baked in), and `src/pwa.ts`, which activates only on `http(s)` so the portable `file://` copy is unaffected. The SW cache prefix `tender-analysis-` must stay unique: the origin `usama-kh75.github.io` is shared with other apps (localStorage too). Likewise the manifest `id` must stay the absolute `/tender-analysis-system/` — Chrome resolves `id` against the *origin*, not the manifest's folder, so `"id": "./"` gave this app the same identity as the contracts-instructions app on the same origin and installing one replaced the other (fixed in v1.2.6; verify with CDP `Page.getAppId`). Changing `id` again orphans every existing install. The installed app's data is separate from the portable file's; moving projects between them goes through the JSON backup.

## Architecture

**Stack**: React 19 + TypeScript, Vite 8, Tailwind CSS v4 (via `@tailwindcss/vite`), `vite-plugin-singlefile`. No router, no backend, no test framework.

**State shape and flow**: `App.tsx` is the single owner of state — an array of `TenderProject` (see `src/types/tender.ts`), held by `useProjectStore` (`src/app/useProjectStore.ts`), loaded from and persisted to `localStorage` via `src/utils/storageService.ts`. There is no reducer/store library: every mutation follows the same pattern — compute a new `Bidder`/`TenderProject`, run it through `calculateBOQMetrics()` (`src/utils/calculations.ts`) to recompute all derived totals/deviations, optionally wrap it with `addAuditLog()`, then `saveProject(updatedProj)` (= `setProjects(prev => prev.map(...))`). A `useEffect` in `useProjectStore` persists `projects` to `localStorage` on every change. Components under `src/components/` are largely presentational plus their own local UI state; the mutation handlers are passed down to them as props.

**Where the handlers live** (since v1.17.2, App.tsx split from 1,801 to ~355 lines with no behavior change):
- `src/app/` holds plain factory functions, not React hooks, because most handlers are created after App's early returns (start screen, loading), where hooks cannot be called. `createEditContext(currentProject, activeBidder, setProjects)` (`editContext.ts`) gives `saveProject`, `commitBidder`, `blockedByOffer` and `fmtNum`. Each factory unpacks it under the old names, so handler bodies read as they did in App.
- `itemHandlers.ts` (row edits, reading correction, tafqeet adoption, stated total, marks, add/delete/duplicate/clear, bidder audit export, page breaks), `offerHandlers.ts` (weighted offer), `importHandlers.ts` (`handleApplyExtractedItems`, `sharedIdentity`, `referenceRows`), `bidderHandlers.ts` (bidder name/add/delete/reset/status, settings, `selectBidder`), `projectHandlers.ts` (create, delete, factory reset, backups, browser, project switch; created before the early returns because the start screen needs `handleCreateProject` and `handleImportBackup`).
- `itemFields.ts`: `withoutBidderPrices`, `SHARED_ESTIMATE_FIELDS`, `READING_FIELD_LABELS`, `syncSharedFieldsToAllBidders`.
- UI pieces moved out of App: `StartScreen`, `ProjectHeader` (ref number, title, bidder switcher/rename/add, tabs; owns its editing state), `AppFooter`.
- `checks/importHandlers.test.ts` covers the four import modes and the weighted-offer refusal through `createImportHandlers` with a captured `saveProject`. Handlers build the new project from the render-time `currentProject`, so two handler calls in the same event overwrite each other: a compound edit (quantity + total, a correction + clearing its flag) must go through a single `handleUpdateItemFields(index, patch)` call. Until v1.8.3, «اعتماد حاصل الضرب» cleared the error flag but left the wrong amount. Also, `calculateBOQMetrics` rebuilds a zero `bidderTotal` from `bidderUnitPrice × quantity`, so clearing a price means clearing every price field (`withoutBidderPrices` in `src/app/itemFields.ts`), not just the total.

**The financial engine is the core domain logic**, and lives outside React entirely:
- `src/utils/calculations.ts` — `calculateBOQMetrics()` is the single source of truth for all derived numbers (deviation %, price ratio, weighted new price, math-error flags). Anything that changes bidder items must go through this function to stay consistent; also home to `parseArabicNumber()` (Arabic/Persian digit + currency-word normalization) and `tafqeetArabic()` (number → Arabic legal spelled-out text).
- `src/utils/bidderAuditEngine.ts` — `parseArabicTextToNumber()` parses Arabic spelled-out amounts (التفقيط) back into numbers via tokenization against `rawNumberMap`, used to detect conflicts between the written and numeric amount (legally, the written form wins per المادة 10/أولاً/ن and ضوابط رقم (4) خامساً/ب/1; the unit price beats a wrong item amount per خامساً/ب/2 — see `HANDOFF.md` §2 for the full legal/math rule table).
  - Tafqeet missing «آلاف» (since v1.14.7, `readMissingThousands`): a number under 100 followed by a hundreds word (200–900) with no thousand or million word, such as «ثلاثة وخمسمائة» (3,500) or «سبعة وعشرون وستمائة» (27,600). It counts only when the digits (unit price or amount) match the reading with «آلاف» added and do not match the literal reading, so «خمسمائة وثلاثة» and «ثلاثة وخمسون ومئة» are never reinterpreted. `parseArabicTextToNumber` stays literal.
    - The row stays flagged: it is the bidder's error (user, 2026-10-12: «حتى ثلاثة وخمسمائة خطأ»). v1.14.6 read it as 3,500 and cleared the flag, which hid the error; v1.14.7 replaces that.
    - The card shows the corrected wording and one button, «اعتماد التفقيط». It goes through `handleAdoptTafqeetThousands`: no number changes, the bidder's text is kept in `BOQItem.originalWrittenText`, and the row counts as committee-corrected (`isCommitteeCorrected`), so the load recheck leaves it alone.
    - Editing the row's reading cancels the adoption openly and restores the text. The export shows the original text and the flag in «واقع الحال», and the correction in «الجدول المعدل».
- `src/utils/recommendation.ts` — `buildRecommendation()` is the single source of the committee's recommendation wording, shared by `ExecutiveSummaryView` and `PrintReportModal`; never recompute it per component. It is derived from all bids (not the active tab): award (committee's explicit choice, else lowest eligible), tie (eligible bids equal or within 1% of estimated cost → ضوابط رقم (5) preference criteria), referral (13/ثالثاً/ب), re-tender (المادة 20). A bidder with no amounts yet (`hasBidAmounts` false) is not a bid: it is left out of the ranking, the recommendation, the summary, the printed محضر, the charts, and the Excel comparison sheet. Before any estimated cost exists (`hasNoEstimate`), the UI shows «بانتظار الكلفة التخمينية», never a zero deviation presented as compliance. The tie wording is contract-type specific via `src/utils/contractTypes.ts` (`TenderProject.contractType`: works/supply/services, chosen in `NewProjectModal` before data entry; consulting services deliberately unsupported).
  - Budget type (since v1.18.0): `TenderProject.budgetType` (investment/operating, chosen in `NewProjectModal`, editable in the settings; a tender loaded without it gets `operating` once, with an audit-log entry, through `defaultLegacyBudgetType` in `normalizeLoadedProject`, because every tender before v1.18.0 was operating-budget (user, 2026-10-21); an unknown value is left alone) feeds `budgetApprovalNote` (`src/utils/budgetTypes.ts`), shown under the award recommendation in `ExecutiveSummaryView` and appended to the award paragraph of the printed محضر. It applies only when the recommended bid is above the estimate, compared on the unrounded `totalDeviationPercent`. Four cases from ضوابط رقم (2) رابعاً: investment ≤10% (1/أ, inform the Ministry of Planning), investment 10–20% (1/ب, ministerial council approval through Planning), operating ≤10% (2, within authority if liquidity exists), operating >10% (2, approach the Ministry of Finance). Investment above 20% prints nothing. An unset type prints nothing and shows a reminder on screen only (`kind: 'missing'`).
  - Tender details (since v1.19.0): four optional `TenderProject` fields, `announcementNo` (1–5), `invitationType` (general/limited/twoStage/direct/singleSource, the methods of article 6; a design competition is deliberately left out because it is not price analysis), `beneficiaryEntity` and `receivedBidsCount`, set in the settings modal and logged in `handleSaveSettings`. `src/utils/tenderDetails.ts` (`tenderDetailParts`) is the single source of their wording. They are display only and feed no calculation or recommendation: they print under the title of the printed محضر, on the tender card (without the counts), and in the first lines of the Excel exports, and only what was entered prints. `receivedBidsCount` may exceed the analysed bids but never be below them (`hasBidAmounts`), so the settings form refuses a smaller number. Unreleased: `announcementNo` is chosen in `NewProjectModal` (default: the first announcement) and shows beside the reference number in `ProjectHeader`, the tender settings and the tenders-window card (`tenderDetailParts` takes `withAnnouncement` so the card does not repeat it); existing tenders are not migrated and stay unset until the committee sets it.
  - The محضر header (since v1.19.0, user decisions 2026-10-23): the title is «محضر تحليل طلبية (referenceNumber)», never «لجنة فتح … والترسية» (the bid-opening committee is a separate body whose minutes this committee receives, and this committee recommends, it does not award). «العدد» and «التاريخ» print blank dotted lines: they are the analysis committee's own minutes number and signing date, written by hand. One real محضر may cover more than one tender; printing several tenders in one محضر is not built yet.

The «توازن العطاء … الحكم» paragraph is an analysis-phase finding: printed next to the recommendation it reads as a second, contradictory recommendation. It is hidden then, and the balance basis is carried by `pricingClause` in «ثالثاً». The weighted-rounding note still prints with its table. Decisions and notes stay in the tender's records (the audit log). User decision 2026-10-21.
  - During analysis (`rec.kind === 'tie'`), when two or more of the close bids are equal to the smallest monetary unit (`equalPriceBids`, not `rec.exactTie`), the summary shows a 📌 note. It names those bidders as the ones to be asked for their initiatives. The print preview's 💡 note says the same (no-print). ضوابط رقم (5) allows completing initiatives only on equal prices. Bids that are only close (within 1%) are compared on what they submitted. `exactTie` needs every close bid equal, so it missed two equal bids beside a third within 1% (the kazket tender). User request 2026-10-21.
  - The price ratio (النسبة السعرية) prints in «أولاً» and «ثانياً» only when weighted prices figure in the محضر (`ratioShown`: an offer that is not paused, a `weighting-required` verdict, or the weighted table ticked). When the committee adopts the bidder's prices as they are, the ratio has no role (since v1.18.5, user decision 2026-10-21).
  - Of the two 📌 notes under an award: the 10/أولاً/هـ «not the lowest» note is `no-print` (since v1.18.5); it is a reminder to the committee. The preference-criteria note (close or equal bids) is deliberately printed, even after the award choice. User decision 2026-10-21.
  - The reason for not weighting («لعدم تجاوز الفقرات غير المتوازنة نسبة (10%)») is printed only when the bid's prices are adopted as they are. With an adopted weighted offer under an `accept-as-is` verdict, `pricingClause` says only «واعتماد أسعار العرض الموزون المعتمد المثبتة في (رابعاً) بقرار اللجنة» (since v1.18.6). The user's general rule for all tenders, 2026-10-22 (الدرب السالك). The budget-approval note (Ministry of Finance above 10%) is unaffected.

That clause is about change-order authority (30%), and the word «موزون» appears nowhere in the instructions. The user asked for it to go on 2026-10-21. An adopted offer is still named through `pricingClause`.

To leave an adopted offer out of a recommendation, the committee pauses the offer («إيقاف المرحلة»); the محضر follows the recorded decision and never hides it (user, 2026-10-21, food tender).

  - Once the committee has chosen the award (`rec.chosenByCommittee`) the arithmetic-correction paragraph is not printed at all (since v1.18.1). The corrections were made with the bidder present and signed, so the محضر never says «صحّحت اللجنة». Their sequence belongs to the tender's records: the audit log, and the signature state written into the audit-log entry of the choice (`handleUpdateBidderStatus`). User decision 2026-10-21; v1.17.2 had kept the row count.
  - Two thresholds (since v1.20.0). `TenderProject.deviationThreshold` is the unbalanced-item limit (item deviation, partial deviation, `assessBalance` counts, the weighted-offer lock in `handleSaveSettings`). `exclusionThreshold` (optional) is the whole-bid exclusion limit (13/ثالثاً/أ): `exclusionThresholdOf(project)` returns `exclusionThreshold ?? deviationThreshold`, so saved tenders need no migration. Everything about excluding a bid or showing the total deviation (`isCommerciallyExcluded`, `buildRecommendation`, `refreshDeviationPrecision`, `formatPercent(totalDeviationPercent, 2, ·)`, `assessBalance`'s third argument, `startOfferBlocker`) uses the exclusion limit. The settings window saves it always, and shows «سند الحد المعتمد» (`thresholdBasis`) when either limit differs from 20; the محضر prints one sentence naming only the limits that differ (a dotted blank when the basis is empty, plus a no-print reminder). The audit log records each change.
  - `eligible` excludes bids the committee disqualified (any reason) and bids beyond the exclusion limit, so the wording says «المؤهلة», never «المؤهلة تجارياً» (only a single bid's commercial verdict is «تجارياً»).
  - Legal texts (since v1.20.0, user decision 2026-10-23): the recommendation in «ثالثاً» names the clause number and does not restate its ruling. Under it `LegalTextsList` (`src/components/LegalTexts.tsx`) prints, for each clause cited (in order, no repeats), its official text between «», from `LEGAL_TEXTS` in `src/utils/legalTexts.ts`. Data: `Bidder.exclusionReasons?: ExclusionReason[]` ({ground, item (1..9, only for `incomplete`), detail}) and `TenderProject.technicalOpinion?` ({source, letterNo, letterDate}). Reasons stay stored if the status changes and are shown and printed only while the bidder is disqualified. `src/utils/exclusionReasons.ts` is the single source of the wording (catalog with label/phrase/legal key/hint, `reasonLine`, `opinionClause`, `exclusionLegalKeys`, `validateReasons`, load-time `sanitizeExclusionFields` in `normalizeLoadedProject` with no `updatedAt` change and no audit entry); the wording was written by Claude on Usama's authority. Rewording only: conditions may not be added (user, 2026-10-23), so words such as «بشرط» ask for confirmation. `recommendationEditChanges` compares the stored basis (kind, bidders, names, amounts) and system text with the current ones and shows a no-print warning; the summary shows basis changes only. The open editor blocks the update (`blockingWork`).
- `src/utils/readingReliability.ts` — reading reliability card (since v1.23.1, 2026-11-03, user-agreed; built on branch `feature/reading-reliability`, shipped on the old interface as `release/v1.23.1`). The app serves many analysis committees, so reading safeguards and their measurement live inside the app with no developer loop (user, 2026-11-03). Three optional `BOQItem` fields, display only, feeding no calculation or print: `readBy` ('ai' | 'ocr', set by `ImageOcrModal.handleApply` for bidder destinations only), `readCheck` (the two reads of the double read differed and the committee has not yet matched the row against the paper; cleared by «طابقتُ الورقة» = `handleConfirmReadCheck`, audit-logged, or by editing the row's reading), `readCorrected` (set by `handleCorrectReading` on the active bidder's row: the measured reading error of this tender, per tender only, no aggregation). `readingReliability(bidder)` returns null for a bid with no read rows (manual or Excel); otherwise the risk rows (readCheck, uncorrected multiplication error, uncorrected tafqeet conflict; committee-corrected and unpriced rows excluded) sorted by amount, largest first, and `ReadingReliabilityCard` shows them above the table (8 first, «عرض الكل»). The audit log was not used for the measure because «تصحيح قراءة» entries carry no `bidderId`. Cleared with the prices (`withoutBidderPrices`), on duplicating a row, and replaced by a fresh read (`bidder_only`/`new_bidder` copy only the new read's marks). «حساسية القرار» (`src/utils/decisionSensitivity.ts`, pure, 2026-11-03, user-agreed, display only): `decisionSensitivity(project)` takes the recommended bid (`buildRecommendation().primary`, the lowest or the committee's choice) against the nearest other eligible bid by amount, sums each side's `readingReliability().riskRows` amounts (rows still to be matched against the paper) and, when that sum reaches the gap between the two amounts, `ExecutiveSummaryView` shows an amber no-print banner «لا تعتمد الترسية قبل مطابقة فقرات بالورقة» with the gap, the unverified sums and row counts per bidder. It is a conservative upper bound (counts a row's whole amount as exposed, no probability, no direction); null with fewer than two eligible bids, no pending rows, or a sum below the gap. Not in the printed محضر or Excel. Not built yet: pre-read advice (handwriting, scan resolution) and (shipped later in v1.23.3) the unit-price outlier signal. Image-quality experiment (2026-11-03, flash, temp 0, pages 10/14/16, 2000px vs 3600px vs 3600px + `mediaResolution` HIGH, two runs each): input tokens were 1520 in all three (a fixed image budget), and the results were inside the noise (4/7 and 4/7; 6/7 and 4/7; 5/7 and 3/7 on page 10's seven disputed rows), so the 2000px/q0.85 constants stay.
- `src/utils/readAdvice.ts` — pre-read advice in `ImageOcrModal` (since v1.23.2, 2026-11-03, built on branch `feature/pre-read-advice`, user-agreed, display only, no changelog entry because it improves an existing feature). Two amber notes above the double-read checkbox, before the user starts reading. (1) **Low scan resolution**, measured locally with no request: for an uploaded image the longest side before `compressImageDataUrl`, for a scanned PDF page the longest side of the embedded image that matches the page's aspect ratio (`scanLongEdge`; a digital page, logo or stamp gives null = unknown, never low); below `LOW_RESOLUTION_EDGE` (1400 px, about 120 dpi on A4) the page is listed. It has to be measured at the source because `pdfToImages` and `compressImageDataUrl` cap every page at 2000 px, which hides a weak scan. `pdfToImages(file, onProgress, onScanEdge)` reports it per page.     - The table bar has one import button (since v1.10.0), which opens `SmartTableImportModal`. The user picks the table type first (bidder / estimate / combined). Excel and CSV stay in that modal for column mapping. PDFs and images (including a pasted screenshot) go to `ImageOcrModal` through `onReadWithAi` → `OcrHandoff {id, files, destination}`, with the destination preset. The combined type is Excel-only, because AI reading extracts a single amount column. `ImageOcrModal`'s early `return null` sits just before its JSX, so the handoff `useEffect` stays above it.
    - The official field names come from the API discovery document (`generativelanguage.googleapis.com/$discovery/rest?version=v1beta`), since the docs pages describe the newer Interactions API instead.
    - The mocked-fetch browser test used to verify this lives outside the repo; there is no UI test suite (pure functions are covered by `npm run check`).
  - `extractBOQFromImage()` — fully offline Tesseract.js OCR. It does **not** just concatenate recognized text: it reconstructs the table geometrically by finding the header row (matching known Arabic BOQ column keywords like ت/الوحدة/الكمية/سعر المفرد/المجموع) via word bounding boxes, then assigns every other word to the nearest column band by x-position (`detectHeaderColumns`/`buildRowsFromHeader`). Falls back to a cruder count-the-numbers-per-line heuristic (`buildRowsHeuristic`) only if no header is detected. This engine handles printed text only — it cannot read handwriting; that requires the Gemini engine. In practice it is also weak on gridded tables: measured mean confidence was 47% for a clean bordered table, 41% rotated 90°, 51% for a scanned page (all garbled) vs 82% for the same content without grid lines. `ImageOcrModal` therefore warns and requires confirmation before inserting when a page's `confidence` is below `LOW_CONFIDENCE` (65). Removing grid lines before OCR is the most promising improvement if the offline engine is ever revisited.
- `src/utils/pdfService.ts` — `pdfToImages()` renders each page of a digital or scanned PDF to a JPEG data URL, which then goes through either OCR engine like any uploaded image. Runs inside the single file and offline: pdf.js runs on the main thread (`globalThis.pdfjsWorker`, no separate worker URL), and its JBIG2/JPX scan decoders (WebAssembly) are embedded as base64 by the `embeddedPdfWasm()` plugin in `vite.config.ts` (virtual module `virtual:pdf-wasm`) and served through a custom `BinaryDataFactory`, because pdf.js otherwise fetches them from `wasmUrl`. This roughly tripled the HTML size (≈3.4 MB, ≈1.1 MB gzip).
- Tesseract hang on first visit: if the offline engine starts while the service worker is still installing/claiming the page, `createWorker` hangs forever at «التهيئة». `extractBOQFromImage` therefore awaits `waitForServiceWorkerControl()` first (no-op on `file://`).
- `src/utils/storageService.ts` — `localStorage` CRUD for projects, `createNewTenderProject()` (a genuinely blank tender with one zeroed bidder per entered name — never build new tenders from `createDefaultProject()`, which is the demo seed), plus `downloadProjectBackup()`/`parseProjectBackupFile()` for JSON export/import of a whole project (the user's substitute for cloud sync/multi-device support, given the no-backend constraint above).

**The «المناقصات» window** (`src/components/modals/ProjectsBrowserModal.tsx`, since v1.13.0) is opened by a Navbar button that shows at every width. The old `<select>` switcher appears only at 2xl.
- It lists every saved tender, most recently updated first. Each card shows the tender's details, its estimate (or «بانتظار الكلفة التخمينية»), and each bidder's corrected total and deviation from the stored `totals`.
- A bidder without amounts (`hasBidAmounts` false) shows «لم تُدخل أسعاره بعد».
- Each card has a «حذف» button (since v1.14.0). Any tender can be deleted, the last one too: «إعادة ضبط النظام» and deleting the last tender leave `projects` empty (stored as `[]`), and `App.tsx` shows `StartScreen` (new tender / import backup) instead of creating a blank tender. The save effect is gated on `loaded`, not on `projects.length`, so an empty list persists. `createProjectHandlers` (with `handleCreateProject` and `handleImportBackup`) is called above the start-screen early return for that reason. An empty browser (no stored key) still gets the demo tender; the start screen needs a stored `[]`.
- «اعتماد المبلغ وتصحيح المفرد (علامة عشرية)» on a multiplication-error card is the ضوابط (4) خامساً/ب/2 exception: the committee adopts the bidder's amount and corrects the unit price to amount ÷ quantity. The bidder's digit goes to `originalUnitPrice`, so it counts as a committee correction in the export.
- Clicking a card opens the tender. Clicking a bidder row also sets `activeBidderId`, without touching `updatedAt`.
- Each tender is shown on its own, with no cross-tender totals or comparison: each tender is a separate committee decision (the user rejected a portfolio dashboard).

**Multi-bidder / multi-page merge logic** (in `handleApplyExtractedItems`, `src/app/importHandlers.ts`, and `ImageOcrModal`'s `processAllImages`) is intentionally conservative: imports merge row-by-row by array index, preserving whichever side (existing table vs. newly extracted) already has real data rather than blindly overwriting — e.g. importing bidder prices never touches `estimatedTotal`, and vice versa. Preserve this merge discipline when touching import/OCR code; it's what prevents an OCR misread from silently clobbering already-verified figures.

**The estimate merge goes by item number** (since v1.14.4), through `planEstimateMerge` (`src/utils/estimateMerge.ts`). The preview notice (`EstimateMergeNotice`) and the insert both use it.
- Merging by position let one dropped row move every later estimate up a row (item 176 on 2026-10-12).
- A table row with no matching reading keeps its estimate. A number read more times than the table holds is applied nowhere. A number not in the table is appended at the end. A reading row without a number is not applied. Any of these asks for confirmation before insert.
- The table's item number is kept as written («٢» matches «2»).
- The estimate still sets quantity and description (user decision, 2026-10-12). The notice lists every quantity and every non-whitespace description it will change, so a misread quantity is visible before it creates false multiplication flags on the bidders.
- A read quantity that differs from the table's is checked against the row's own amount (since v1.14.5, `quantityEvidence`). With a read unit price, the table's quantity is kept when unit price × table quantity equals the amount and unit price × read quantity does not. Without a unit price, the same test is a whole-number price. The notice lists these rows as kept. A read quantity that fits neither is still applied and flagged «لا يوافقها مبلغ الفقرة». Gemini reads the same scan differently each time, and 1,150 for 1,155 recurred on 2026-10-12.
- It merges by position only when the table has no real rows (a new tender) or the reading has no item numbers. An Excel estimate without an item-number column leaves `itemNo` undefined instead of inventing one from the row index.
- The bidder merges are still by position.

**Quantity is shared, and a bidder import keeps the table's quantity** (user decision, v1.11.10):
- Both `bidder_only` and `new_bidder` keep the table's quantity. They clear the extracted flags so `calculateBOQMetrics` rechecks the row with that quantity.
- Both previews list rows whose quantity differs (`quantityMismatches` + `QuantityMismatchNotice`), so the committee can fix the table quantity by hand if it is the wrong one.
- A blank placeholder row («فقرة N», quantity 1, no estimate, no bidder amount; `isBlankRow`) is not a reference, so the file's quantity applies there.
- An estimate import sets the quantity. Bidder rows whose quantity changed are rechecked, except committee-corrected rows.
- A file without a quantity column leaves quantities unchanged; `mapImportRows` returns `undefined`, not 1.
- `SmartTableImportModal.mapImportRows` is the single row mapping for both the preview audit and the insert. Keep them on it.
- Item identity is shared too (since v1.12.2). Both bidder merges take `itemNo`, description and unit from `sharedIdentity` in `src/app/importHandlers.ts`:
  - An existing row keeps the table's values. The file's values apply only to a new row or a blank placeholder row.
  - Before this, a new bidder overwrote everyone's descriptions. Both paths also dropped `unit`, which `calculateBOQMetrics` then defaulted to «عدد» for every bidder.
- The merges pass the read unit price as `bidderUnitPrice` as well. `calculateBOQMetrics` derives a missing amount only from that field, so an amount that was not read is computed with the table quantity.
- A Gemini quantity that was not read stays `undefined`, not 1, and the reading window marks it. An amount that was not read is derived only from a quantity that was read. Otherwise it stays empty, with `enteredBidderTotal` undefined, so no recorded zero gets flagged.
- `mapImportRows` drops summary rows (`kept`) in two cases:
  - **Total word (`SUMMARY_WORD`):** «مجموع» or «إجمالي» as a whole word, never «مجموعة». The row is dropped if it has no item number or no amount.
  - **Total label (`TOTAL_LABEL`):** a label that is only a total phrase («المجموع», «مجموع الصفحة», «Grand Total»). This applies even when the row has a number and an amount.
  - It also drops a text label in the item-number cell with no description but with an amount (the totals block under a table).
  - A dropped row shifts the index merge, so never drop by substring alone.
- `autoDetectRoles` checks in this order: item number, description, computed columns («×», فرق, نسبة, موزون… → ignore), tafqeet, estimate, unit price, quantity, amount. Checking unit price first made «سعر المفرد كتابةً» a unit price, and made «الكمية × المفرد» the unit price whenever it came first.
- An import with no amount column stops with a message: no estimate-amount column for an estimate, no amount or unit-price column for a bid, and for a combined table (which replaces the whole table) a missing estimate-amount column or a missing bid amount or unit-price column. It used to write 0 over the existing values.

**Load safety and precision** (since the 2026-10-13 third-party review):
- `getAllProjects` never overwrites unreadable data. Unparsable text, a non-array, or an element that is not a tender is copied to the `antigravity_tenders_recovery_v1` key first (`getRecoveredData`), and `RecoveryNotice` offers it for download. Each project loads on its own, so one bad tender no longer drops the rest. Its ✕ deletes that copy for good, so it asks for confirmation unless the copy was downloaded in this session (since v1.17.1).
- Dates shown to the user or put in file names (backups, recovered data, a new tender's `submissionDate`) use `localDate()` (`src/utils/localDate.ts`, device time), never `toISOString().split('T')[0]`, which is the UTC date and names a backup saved after midnight in Iraq with the previous day (since v1.17.1).
- `totals.totalDeviationPercent` keeps six decimals, because exclusion compares it with the threshold (20.004% used to be stored as 20.00 and pass). Display goes through `formatPercent(val, 2, threshold)` / `percentDecimals`, which adds decimals only when the rounded figure would sit on the limit. Old stored projects are refreshed on load by `refreshDeviationPrecision`, and only a flipped exclusion is logged.
- The multiplication check runs for every quantity above 0 (`quantity > 0`), so fractional quantities such as 0.5 and quantity 1 are checked (quantity 1 since v1.15.3).
  - Trial on the real backups (2026-10-14): 56 quantity-1 rows with both a unit price and an amount, 2 differ, both genuine (amount 9,700× and 6× the unit with table quantity 1), no false positive. Both were unflagged «سليم» before.
  - Known trade-off: a table whose quantities were never entered (all 1) with a unit price and an amount both read is flagged row by row. That is a prompt to enter the quantities, so no exemption was added; enter the estimate (with quantities) before the bid, as the normal flow does.
  - Commit 5a61c97 (2026-08-24) had exempted quantity 1 for direct unit-price tables; there the unit price equals the amount, so nothing is flagged.

**Backup reminder** (since v1.17.0). Data lives only in the browser, so the app reminds the user to save it to a file.
- `src/utils/backupStatus.ts` stores, per tender, the time of the last backup that contains it, under the key `antigravity_tenders_backed_up_v1`.
- A tender is unsaved when its `updatedAt` is later than that time, so every handler that changes a tender's data must update `updatedAt`.
- The Navbar button saves the all-tenders backup. A single-tender backup updates only that tender's mark, and a full restore counts as a backup.
- `beforeunload` fires only while unsaved changes remain. Reloads the app asks for itself (update, extension notice) call `allowUnload()`.
- `saveJsonFile` uses `showSaveFilePicker` with `id: 'tender-backups'` so the browser remembers the folder, falls back to a normal download when it is unavailable, and a cancel is not recorded as a backup.

**Browser extensions that rewrite the page** (since v1.15.5). TransOver, a hover-to-translate extension, replaces the text node under the mouse with a new one; Chrome's own translation wraps text in `<font>`. React keeps the old node, so a later insert next to it throws `NotFoundError: insertBefore` and the whole app went white (the user's installed app, 2026-10-14, «إلغاء الاعتماد» → «اعتماد العرض»). It can also leave a shown figure stale.
- `src/utils/foreignDom.ts` watches `#root` for the first foreign element (FONT, hyphenated, or `HTMLUnknownElement`), and `ForeignDomNotice` (under `RecoveryNotice` in `App.tsx`) tells the user to disable the extension for this site.
- `RenderErrorBoundary` wraps `<App/>` in `main.tsx`: a render crash shows «تعطّل عرض الصفحة» with a reload button instead of a white screen. The change that crashed the render is already saved (checked).
- `index.html` has `translate="no"`. Headless Chrome has no extensions, so such crashes do not reproduce in the test scripts: ask the user for the Console error early. A global `Node.prototype.insertBefore` patch was rejected (it hides the crash and leaves missing or stale elements).

**Legal/audit framing matters for UI behavior**: arithmetic correction is the committee's act, notified to and signed by the bidder (ضوابط رقم (4) خامساً/ب/3), so the system never silently auto-corrects a bidder's submitted numbers — math-error and text-discrepancy detection only *flags* rows (`hasMathError`, `hasTextDiscrepancy` in `BOQItem`); correction is an explicit, logged committee action (see `correctionRationale`, `AuditLogEntry`). Keep this "detect and flag, never silently rewrite" pattern when adding audit features. Stored flags are sticky, so `recheckStoredFlags` (`storageService.ts`, since v1.12.2) runs them again on every load and backup restore:
- It covers only rows the committee did not correct (`isCommitteeCorrected`), and skips rows with an amount but no recorded amount.
- It logs every change as «إعادة فحص تلقائية».
- It fixes flags left stale by older parsers (item 41) or missing flags.
- It changes flags only, never amounts.

**A plain edit in the main table is a reading correction, not an arithmetic one** (since v1.11.7). Editing the quantity, unit price, item amount or tafqeet goes through `handleCorrectReading` in `src/app/itemHandlers.ts`, not `handleUpdateItemFields`:
- The new value becomes the bidder's recorded value (`enteredUnitPrice`/`enteredBidderTotal`).
- Both flags are cleared so `calculateBOQMetrics` recomputes them. Stored flags are otherwise sticky.
- No other number changes. A unit-price edit fills the amount only when it is empty, so a real multiplication error is never hidden.
- A quantity edit rechecks that row for every bidder.
- A committee-corrected row (`bidderTotal` ≠ a non-zero `enteredBidderTotal`) asks for confirmation first, then cancels the correction openly, with a log entry.
- `AmountInput` commits on blur or Enter, and Escape cancels; it no longer commits per keystroke.
- «الأرقام كما في الورقة (خطأ قراءة لا خطأ مجهز)» (since v1.23.0, `handleAcceptAsReading`): on a row whose committee correction is on the numbers (`hasNumericCommitteeCorrection`, not the tafqeet-thousands adoption), the committee confirms that the currently adopted unit price and amount are what the bidder really wrote and the reading was the error. They become the recorded values, the correction and the bidder's signature mark drop, and an audit entry «تصحيح قراءة» keeps the old reading. The tafqeet is untouched. User's observation 2026-11-01: the system treats every change after reading as a committee correction, while Gemini misreads are self-consistent (unit price, tafqeet and amount wrong together). A second reading on enlarged strips was tried the same day and rejected (no better results); do not propose it again.
